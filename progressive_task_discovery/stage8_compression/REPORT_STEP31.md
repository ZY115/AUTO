# Stage 8 第三十一步（P3）：最简单的学习型抽象，按验收标准是负结果

P3 要做的是把归属键从 177 往 86 推，而且必须落在 `(冗余查询, 漏推进)` 平面上现有点的左下方。
实现了最简单的一版：**部分反馈签名 + 支持度门槛 + 后继闭包**，不碰神经网络也不碰概率模型。

结论：**它确实省了查询（关闭 16% 到 21% 的缺口），但每一个变体都在漏推进上付费，学习也明显变慢。
没有任何一个变体落在验收要求的左下方。**

## 1. 规则

每个历史维护一个签名：对每个事件记 推进 / 忽略 / 致命 / 未知。两个历史可以共享，当且仅当

- **没有任何事件上两者都有记录且记录不同**（兼容），且
- **在至少 `support` 个事件上两者都有记录且一致**（支持度门槛）。

支持度门槛是必需的：一个全新历史的签名全是"未知"，与任何东西都兼容，没有门槛就会并入任意类。

**后继闭包是这一版唯一的非平凡设计。** 第一次实现用的是"先按签名分组、再按后继细化"，
结果几乎不合并（73 类 / 73 节点）。原因很具体：在前缀树里两个被合并的节点有各自不同的后继，
细化时后继落在不同类，于是把父节点又劈回去，级联下来只剩单例。**合并必须在做的时候就把后继
一起带走，任何一处矛盾就整体回滚。** 这就是经典状态合并的形状，只是把访问次数配额换成了签名
支持度。改成闭包之后类数从 73 降到 20 到 34。

## 3. 按验收标准判定：不通过

要求是在 `(冗余查询, 漏推进)` 上落到现有点的左下方。实际位置：

| 点 | (冗余, 漏推进) | 达标步数 | 解出 |
| --- | --- | --- | --- |
| node | (91.3, **0.0**) | 1,281 | 144/144 |
| 签名 support=4 | (77.9, **70.4**) | 5,427 | 141/144 |
| 签名 support=3 | (75.9, **153.0**) | 15,115 | 133/144 |
| oracle | (0.0, 0.0) | 1,281 | 144/144 |

**向左移了，但同时向上移了。** 除 oracle 外，`(·, 0)` 上只有 node 一个点。而且代价不只体现在
漏推进这个计数上：达标步数从 1,281 涨到 5,427 至 40,000，解出从 144/144 掉到 141 / 133 / 115。
**用 1.12 倍的查询节省换 4 到 31 倍的学习变慢，不划算。**

单个任务上曾出现过一个"support=3 省 32 次查询、零漏推进、步数不变"的点，**放到 24 个族上
不成立**。这是本项目第三次被单任务探针误导，记在这里。

## 4. 诊断：签名兼容不是任务状态等价的可靠代理

原因可以说得很确切：**在已观察的事件上一致，对未观察的事件没有任何约束。**
平均每个节点只有 2.6 个事件有证据（共 7 个），两个节点的证据平均重叠 1 到 2 个。
于是"在 3 个事件上一致"这件事，留下 4 个事件完全不受约束，而任务状态的区别常常正好在那里。

支持度门槛提高只能缓解不能消除：support=4 把漏推进从 153 压到 70，但也把节省从 21% 压到 16%，
而且仍然不是 0。**这条曲线上不存在"零漏推进且省查询"的点。**

所以一个可用的规则需要的不是更高的门槛，而是别的东西——要么要求两者在**同一组**事件上都有证据
（而不只是在重叠处一致），要么对未观察项的风险给出上界。这是下一个具体问题。

## 5. 对 P4 的判断

按原定条件，"如果确实能明显从 139 向 85 靠近再去 CraftWorld"。**目前最好的安全点仍是 node 的
177，学习型抽象只在付出漏推进的前提下到 158。所以不满足去公开长任务的条件。**
