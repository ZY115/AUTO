## 风险对照是构造出来的，不是开关

这一节必须先读懂，否则会跑出一个看似正常、实则无效的对照。

直觉做法是把配置里的 `use_lava` 从 `true` 改成 `false`。**这是错的。**

危险格会占掉网格上的一个位置、挤走原本在那里的物体、并且消耗随机数发生器的抽取，
于是后续所有物体的坐标整体错位。实测：`book-and-quill`、`environment_seed=0`，
关掉岩浆之后 workbench 和 squid 的坐标都变了。那样比较的就不只是「有没有危险」，
而是「有没有危险 **加上** 换了一张地图」。

**正确做法**：两个条件用**同一张含岩浆的网格**，安全那格把任务层级里的「拒绝状态」中和掉
（`neutralize_deadends: true`，补丁 01 提供）。结果是：

- 网格、物体坐标、起点、可观测集、可能观测集 —— 逐项相同
- 危险格**照样能走进去**，不变成墙，所以**图上的**最短路长度不变
- 唯一区别：踩上去这一局结不结束

**但要说清楚一处，早先这里写错了。**「图上最短路不变」不等于「成功轨迹的最短长度不变」：
一条穿过危险格的路在 lava 条件下不再可用，安全策略可能必须绕行。所以这个干预
**不是**纯粹的「踩上去会不会死」，它同时改变了可行解的长度。这是死路这种干预的固有性质，
消不掉；但分析时必须把它算进去，不能声称两个条件的任务难度只差一个终止标志。

已验证：随机策略在 lava 条件下 92 幕全部死于岩浆；在 safe 条件下踩上去 226 次，
一次也没有终止。`tools/verify.py` 的第 3 项检查的就是这个。

`tools/run_grid.py` 已经内置了这个做法，你不需要手动配置。

## 阶段一：表格版全网格（必须跑）

```bash
cd /path/to/AUTO
$HRM_PYTHON tools/run_grid.py \
    --state-format tabular \
    --episodes 200000 \
    --seeds 3 \
    --workers <你的核数> \
    --work /scratch/hrm \
    --out results/runs/linux_tabular_200k.jsonl
```

**36 次运行** = 3 个任务 × 2 种风险 × 2 个臂 × 3 个种子。
每次运行内部包含 10 张地图，一共 360 条实例记录。

**360 是记录数，不是 360 张独立地图。** 每个任务只有 **10 张不同的地图**，
在 2 风险 × 2 臂 × 3 种子下反复使用。统计时的独立单位是这 10 张地图，
不是 30 个「地图 × 种子」——把后者当独立单位是伪重复，会把区间算窄。
`analyze_grid.py` 现在两种都打，以成组的那个为准。

参考耗时：M1 Pro 十核外推 **12 到 18 小时**。核多按比例缩短。

**这一阶段的目的是把 H2 测出来。** 表格版够快，能跑满原作者的二十万幕。

## 断点续跑

`run_grid.py` 会读取已有的输出文件，**跳过里面已经成功的运行**。
所以中断之后、想加种子、想加任务，都直接重跑同一条命令，不会丢掉已完成的工作：

```bash
# 先跑 3 个种子
$HRM_PYTHON tools/run_grid.py ... --seeds 3 --out results/runs/x.jsonl
# 后来想加到 5 个，同一条命令改个数字，只会补跑新增的那 2 个
$HRM_PYTHON tools/run_grid.py ... --seeds 5 --out results/runs/x.jsonl
```

失败的运行不会被记为已完成，重跑时会自动重试。

## 怎么估时间

**成本由「环境步数」决定，不是「幕数」。** 带岩浆的幕很短（智能体很快就死），
无岩浆的幕会跑到 1000 步上限，两者相差 30 倍以上。

M1 Pro 单进程（`OMP_NUM_THREADS=1`）实测：

| 配置 | 速度 |
|---|---|
| 表格，有岩浆 | 54 幕/秒 |
| 表格，无岩浆 | 5–10 幕/秒 |
| 神经 `full_obs`，训练已开启 | **0.54 幕/秒** |
| 神经，尚未开始训练 | 有岩浆 12 幕/秒 / 无岩浆 0.33 幕/秒 |

### 两个会让你估错的陷阱

**一、`er_start_size` 的发表值是 100000。**
回放缓冲填满之前，**一次梯度更新都不会发生**。低于约 1000 幕的短跑只测了走路、
没测训练，拿它外推会低估几十倍。要测速就临时加 `--er-start-size 3000`，测完去掉。

**二、规模是次线性的。**
实测 cake 带岩浆的表格臂，1 万幕用 185 秒，4 万幕用 482 秒——
系数 **0.65**，学会之后每幕反而更便宜。按线性估会高估。

### 关于 GPU 的诚实提醒

网络很小（144,147 个参数），批大小 32。瓶颈很可能在**纯 Python 的环境步进**上，
不在网络上。**多核并行（同时跑多个 run）大概率比换一块更强的 GPU 收益更大。**

我们在 Apple 芯片上试过 MPS：比 CPU 还慢（0.40 对 0.54 幕/秒），
小批量下 kernel 启动开销压过了收益。CUDA 上未必一样，但请**先用阶段二的探路网格
在你自己的机器上实测，再决定排期**，不要假设 GPU 一定快。

## 看结果

```bash
python3 tools/analyze_grid.py results/runs/*.jsonl
```

不带参数时默认读 `results/runs/*.jsonl`。

输出**三套口径**，缺一不可：

- **末段成功率**：最后四分之一的平均成功率。**有上限。**
- **RMST**：`E[min(达标幕数, 20万)]`。没达标的实例按整个预算计入，所以**不丢数据**。
- **交互项**：按三种尺度分别打印，见下。

**为什么必须三套一起看。** 20 万幕的安全条件下两臂末段成功率都是 1.000、差 +0.000，
看起来「没差别」；换成 RMST，同一批运行差 5 到 26 倍。**有上限的指标在饱和之后
就不是效应量了**，这个错误本项目犯过三次，所以工具每次都一起打出来。

### 达标时刻记在窗口的哪一端

判据是「连续十个评估点平均达到 90%」。评估间隔 100 幕，所以这个窗口横跨 900 幕。
把时刻记在**窗口起点**是回溯标记——用了随后 900 幕的信息，却把时间记回窗口开始，
不是任何在线判据能给出的时刻。记在**窗口末端**才是首次确认达标。

**对快的臂这是数量级差别**：book/safe 的 Y11 在起点定义下 RMST 是 113 幕，
在末端定义下是 1,013 幕，共享的加速倍数随之从 37.15x 变成 **5.04x**。

默认用末端。两种定义都合法，但**必须写明用的哪一种，且不得混用**：

```bash
python3 tools/analyze_grid.py --anchor=start results/runs/*.jsonl
```

### 「倍数」有两个，它们不相等

这是本项目**犯过两次**的错误，所以工具现在把两个都打出来：

| | 定义 | 先做什么 |
|---|---|---|
| **A** | `mean(Y10) / mean(Y11)` | 先在实例上取平均，再相除 |
| **B** | `exp(mean(log(Y10ᵢ / Y11ᵢ)))` | 先逐实例相除，再取对数平均 |

逐实例比值一偏斜两者就分开。神经版 book 的 lava 格上 **A = 3.64x、B = 4.28x**，
差 18%；对应的交互是 **1.85x 与 2.19x**。

两个都是合法摘要。**但报任何一个都必须写明是哪一个**，而且——

> **关于 A 的论证不能套到 B 上。**

具体一次教训：曾用「截断把 `mean(Y10)` 压在 τ 以下，所以倍数有上限」来解释一个
数字，而那个数字其实是 B。截断上限的论证只对 A 成立。

### 交互项有方向，但方向属于你指定的尺度

同一批数据可以同时成立以下三句，它们**并不矛盾**——加性交互和乘性交互本就是不同的量：

| 尺度 | book 上的交互 | 说的是 |
|---|---|---|
| 末段成功率之差 | `+0.464` | 危险下共享带来更大的成功率提升 |
| RMST 节省量（加性） | `+44,553 幕` | 危险下共享节省更多训练幕数 |
| RMST 倍数（乘性） | `0.292x` | 危险下共享带来的相对加速**更小** |

每一条都有自己的限制，报告时要一起写：末段成功率在 safe 格封顶（两臂都 1.000，
差只能是 0）；加性量受量纲支配（岩浆下两臂本来就要十万幕级）；乘性量受截断压缩
（岩浆下 Y11 已用掉大半预算，倍数上限有限）。

**能成立的写法**：「交互方向依赖所选指标与尺度」。
**不能成立的写法**：不加限定的「不可逆性放大复用收益」，或者反过来的
「两套数字都不是效应量」——固定预算是研究问题的一部分，不自动构成测量伪影。

配对单位是**地图**，不是「地图 × 种子」。自助只重抽这 10 张地图；
旧的按 30 个配对差重抽仍会打印，但标记为仅供诊断。

两臂都在地板上时（岩浆下的 book-and-quill 与 cake），数字**照常打印**并注明地板限制。
早先的版本会直接拒绝打印，那等于按结果方向决定是否报告。也不要从曲线形状推断
「加预算有没有用」——那个推断曲线撑不住。

## 协议：默认只跑作者自己的设置

`--protocols` 默认是 `author`，对应 `pseudoreward_after_step = 0.0`，**没有每步惩罚**。
这是原作者配置里的值。

我们早期自己加过 −0.01 的步进惩罚，结果让一个对照方法看起来完全崩溃；
去掉之后它反超。**不要擅自加步进惩罚。** 如果要研究这个因素，
把它当成一个显式的对照条件跑：

```bash
--protocols author,stepcost
```

然后在报告里把两种协议分开写，不要混成一个结论。

## 第三臂：C-full（跨状态经验传播对照）

Y11 与 Y10 同时改变了两件事——参数是否跨状态共享，以及一条经验能否影响别的任务
状态下的策略。所以 `Y11 − Y10` **不能读成参数共享的价值**。C-full 把两者分开：
参数照 Y10 那样独立，但每条经验广播到**每一个合法状态的技能库**。

| 臂 | 参数组织 | 每条经验更新到哪里 | 每步更新预算 |
|---|---|---|---|
| Y10 | 每状态一套 | 当前状态的库 | 该库自己的采样规则 |
| Y11 | 跨状态共享一套 | 共享库 | 同上 |
| C-full | 每状态一套 | **所有合法状态的库** | 每个库各自采样 |

```bash
$HRM_PYTHON tools/run_grid.py --arms Y11,Y10,Cfull --tasks book ...
```

**这是跨状态经验传播对照，不是 Icarte 算法的复现**：option 定义、伪奖励、终止
语义全部沿用当前 HRM 实现，只改传播范围。

### 先跑验收检查

```bash
$HRM_PYTHON tools/cfull_equivalence_check.py
```

六项，核心是第一项：**全目标更新下 C-full 必须与 Y11 逐位相同。**

理由是表格 Q-learning 的一条性质：若干张初值相同的表，收到相同顺序、相同目标集合、
相同伪奖励的更新，会始终保持相同。全目标更新（`formula_update_sel_num: null`）下
没有采样、不消耗随机数，于是所有库始终等于那张共享表；行为策略读的又是当前状态的库，
所以连轨迹都相同。

**这条通过意味着什么。** 在这个受控设置下，**参数共享就是「避免重复计算和存储」
的一种实现方式，本身不含学习内容**。因此在线实验里 Y11 与 Y10 的差异，必须从
采样、经验分配、探索计数这些环节去解释，**不能直接命名为「参数共享的收益」**。

这只是验收条件。正式实验仍保留各臂独立的计数器与采样，**不要求在线行为相同**——
第三项检查反过来要求它们必须不同，否则说明广播没有生效。

### 三个实现细节，每一个搞错都会测成别的东西

1. **未访问的状态也要能收到更新。** 库是按合法状态预建的，不是首次访问时才建。
   只广播到已存在的库，测到的是「访问之后才共享」，是另一种更弱的机制。
2. **伪奖励对接收方必须正确。** 已验证它只是 `(formula, observation, is_terminal,
   is_goal_achieved)` 的函数，不读任何任务状态，所以同一条经验在每个库里产生同一个
   伪奖励。检查 0 对着活代码断言这件事，上游一旦改动会立刻失败。
3. **更新一次 Q 值不等于执行了一次技能。** 执行计数走 `_get_policy_bank`，只落在
   当前状态的库上，所以广播不会抬高执行计数、不会加速 ε 衰减。两个计数分开报告。

### 成本要单独记

C-full 每步做「合法状态数」倍的 TD 更新——在 frl-bq 的层级上是 **20 倍**
（实测 6,810 环境步产生 136,200 次更新调用）。

所以配平分两层，**不要强行让同一组对照同时配平环境经验与计算量**：

- **主实验**固定环境交互预算，比较样本效率，同时记录实际 TD 更新数、元控制器
  更新数、内存与墙钟。
- **C-budget**（第二步）再做计算受限的消融：所有库合计每步最多 4 次更新，采样规则
  预先固定、覆盖所有合法「状态—目标」对，**不得按结果挑最有利的分配**。即便如此，
  相同更新数也不等于相同墙钟成本。

注意「同幕数」不是「同环境经验量」：失败早结束的一幕与长成功轨迹消耗不同。

### 预先接受的三种结果

- C-full 接近 Y11、明显优于 Y10 → 跨状态经验传播能替代较多共享收益。
- C-full 接近 Y11，但 C-budget 明显落后 → 共享的价值包含「以较少更新传播学习结果」。
- C-full 仍落后 → 继续查探索计数、采样与目标语义，**不能把剩余差距直接命名为
  「纯参数共享收益」**。

## 单因素条件：`tools/single_factor_checks.py`

`crossstate_shared_sampling` 本来**不能**当单因素开关用，有两条附带影响：

1. **更新采样与行为探索共用 NumPy 全局流。** 改了抽哪些子目标，就会平移之后每一次
   探索用的随机数——差距变了也分不清是采样造成的还是随机数错位造成的。
2. **探索日程本身两臂就不同。** ε 按**当前库**的执行计数退火，Y11 合并计、
   C-full 分状态计，所以 Q 表一样时 ε 也不一样。

两个新开关把这两条关掉，**都默认关闭**，不影响任何已记录的结果：

| 参数 | 作用 |
|---|---|
| `separate_update_rng` | 每个库自己的更新采样生成器，全局流留给行为策略 |
| `subgoal_exploration_rate_const` | 把 ε 钉成常数 |

```bash
$HRM_PYTHON tools/single_factor_checks.py
```

四项，**比的是每一步的动作，不是回合摘要**——摘要一致是弱得多的证据，本项目
已经在这上面吃过一次亏：

```
S1  分离更新流的开关默认关闭，结果与从前一致
S2  打开后行为序列改变（更新采样确实移出了全局流）
S3  固定 ε + 分离更新流 + 共用采样 → 两臂逐步动作完全一致    ← 核心
S4  同条件下关掉共用采样 → 两臂不一致（S3 非平凡）
```

### 两个必须播种的地方

**每个库要有各自不同的种子。** per-state 的库是从一个模板深拷贝出来的，
深拷贝会连生成器状态一起复制，不重新播种的话所有库会抽到相同的子集——
那等于**意外打开了共用采样**，而共用采样本该是显式开关。播种用 `zlib.crc32`
而不是 `hash()`：Python 的字符串哈希每进程随机，除非设了 `PYTHONHASHSEED`。

**共用采样那一次抽取，必须用与 Y11 单库同种子的流。** 第一版从"当前正在行动的
库"抽，而每个库种子不同，于是 C-full 的子集序列从第一步起就与 Y11 不同——
各库彼此一致了，却和 Y11 不一致。S3 因此失败在第 1,436 步（Q 表在第 440 步
就已分叉）。这不是发现了新通道，是检查本身设计错了。

### S3 通过意味着什么

只意味着：**在固定 ε、分离随机数流、共用采样这三个条件同时成立时，
剩下的唯一差异就是各库独立采样，而去掉它两臂逐步一致。**

它**不**证明在线实验里的差距来自采样——在线实验里 ε 不是固定的，随机数流也不
分离。它只是让后续的干预实验具备了"只改一个因素"的资格。
