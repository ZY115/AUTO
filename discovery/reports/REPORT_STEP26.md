# Stage 8 第二十六步（P0）：错位、缓存与证据归属审计

问题是：**现有的负面结果有多少来自错误缓存，而非查询策略本身。**

标签是按 agent 的历史节点归档的。一旦它跳过一次本该推进的查询，历史就与任务错位，此后所有
标签都被写进、也被读自一个描述着**另一个任务状态**的节点。第二十四步指出了这个机制，这一步
把它量出来，并与策略本身分开。

三种缓存设置，其余全部相同：

| 设置 | 含义 |
| --- | --- |
| 节点 / 复用 | 此前所有实验的做法 |
| 节点 / 不复用 | 从不重用已记录的标签，每次触发要么付费要么未知；把策略与缓存彻底隔离 |
| **真状态 / 复用** | **特权**：按真实任务状态归档标签。这是"完美证据归属"的样子，只作上限参照，不是方法 |

计数器纯属测量，没有任何一臂的行为依赖它们。24 个族 × 4 个种子 × 2 档预算。

## 2. 四条结论，逐条回答 P0

**第一，最好的两个策略根本不错位，所以第二十四步的 21% 没有被污染。**
`arrival` 在 20 万步里只错位 1 步，缓存用错 0 次；`novel` 错位 77 步，用错 19 次，漏掉推进 0 次。
**它们的结果是干净的。** 这条是 P0 最重要的产出：先前的正面结论不需要重做。

**第二，`random` 的崩溃有相当一部分确实是归属问题，但不是全部。**
同样的预算、同样的策略，只把标签按真实任务状态归档，解出率从 **3/96 升到 41/96**，达标快 1.53
[1.31, 1.82] 倍。它漏掉了 4,585 次推进，是全表唯一一个漏推进达到四位数的臂。但修好归属之后
它仍有 55/96 失败，**所以随机跳过既是归属问题也是信息问题，不能只归因于一边。**

**第三，`decision` 的天花板不是归属问题，修好归属反而更糟：77/96 掉到 20/96，0.25 [0.17, 0.35] 倍。**
原因是它只在"这个历史下还不知道该做什么"时提问；完美归属让标签在同一任务状态的所有历史间共享，
于是节点更早地不再"茫然"，它问得更少（27 → 24 次），学到的更不够。**完美的归属让懒惰的策略更懒。**

**第四，缓存是必需的，不是负担。** 关掉复用之后每个策略都垮掉（0 到 61/96），
`arrival` 用满 320 次预算仍只解出 61/96。**缓存的错误远小于没有缓存的代价。**

## 3. 一个此前没有的数字：归属的上限是 2 倍，结构现在拿到四分之一

四臂结果完全相同（96/96、1,271 步），只有查询次数不同：

| 做法 | 用掉查询 | 相对基线省 |
| --- | --- | --- |
| 基线 arrival | 173.4 | 1.00 |
| 结构规则 novel | 138.8 | **1.25 [1.21, 1.29]** |
| 完美归属 arrival | 84.9 | **2.04 [1.92, 2.15]** |
| 两者兼得 | 77.4 | 2.24 [2.10, 2.36] |

**合并本身就是近似的证据归属**，所以这两件事不是叠加的：完美归属单独就拿到 2.04 倍，
结构在它之上只再添 10%。反过来说，**第二十四步的 21% 是一个 2.04 倍机会里的四分之一。**

预算收紧到 160 时，完美归属的价值急剧放大（仍是 `arrival`）：

| 量 | 节点归档 | 真状态归档 |
| --- | --- | --- |
| 达标步数 | 19,857 | 1,271（**15.6 倍**） |
| 查询次数 | 136 | 85 |
| 解出 | 85/96 | 96/96 |

**查询越紧，归属越值钱。**

## 4. 对那条假设的处理

"修复错位是扩大收益的唯一方向"——这一步**部分支持、部分否定**，仍应作为假设而非结论：

- **支持**：归属的上限是 2.04 倍，远大于结构当前拿到的 1.25 倍；预算紧时上限到 15.6 倍。
- **否定**：最好的两个策略压根不错位，它们从完美归属里得到的**不是"修复错位"，而是"在等价历史之间共享证据"**。那正是一个正确的自动机所做的事，与"检测错位"是两件不同的事。
- **反例**：`decision` 在完美归属下更差，所以"更好的归属"不是对所有策略都是改进。

准确的说法是：**在这套接口里，可改进的空间主要在证据归属，而不在查询策略；而"错位检测"只对会错位的策略有用。** 真状态归档是特权参照，不是可实现的方法。
